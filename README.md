# Контейнеры: Big O против секундомера

На лекции мы оценивали контейнеры через Big O: вставка в середину списка —
O(1), в середину массива — O(n). В этой работе вы проверите это
экспериментально и выясните, почему реальное время часто расходится с
асимптотикой.

Работа состоит из двух частей:

1. **Код** (проверяется автоматически): три структуры данных и четыре
   сценария нагрузки, результат которых детерминирован.
2. **Отчёт** `REPORT.md` (проверяется на защите): замеры, графики и выводы.

## Часть 1. Структуры и сценарии

### Три структуры

| Структура | C++ | Rust | Zig | Go | Python |
|---|---|---|---|---|---|
| `array` — непрерывный динамический массив | `std::vector` | `Vec` | `std.ArrayList` | слайс | `list` |
| `linked` — двусвязный список | `std::list` | `LinkedList` | `std.DoublyLinkedList` | `container/list` | **свой** (см. ниже) |
| `deque` — двусторонняя очередь | `std::deque` | `VecDeque` | `std.Deque` или свой кольцевой буфер | **свой** кольцевой буфер | `collections.deque` |

### Генератор чисел

Чтобы у всех языков получался одинаковый результат, используется
**splitmix64** (все операции по модулю 2⁶⁴). В шаблоне он **уже реализован**
на всех пяти языках, писать его заново не нужно:

```
state = seed
next():
    state = state + 0x9E3779B97F4A7C15
    z = state
    z = (z xor (z >> 30)) * 0xBF58476D1CE4E5B9
    z = (z xor (z >> 27)) * 0x94D049BB133111EB
    return z xor (z >> 31)
```

Проверка: при `seed = 0` первые три значения —
`16294208416658607535`, `7960286522194355700`, `487617019471545679`.

Ниже `rnd()` означает `next() mod 1 000 000`, а `next()` — полное 64-битное
значение.

### Четыре сценария

| Сценарий | Что делает | Для каких структур |
|---|---|---|
| `push_back` | `n` раз: добавить `rnd()` в конец | все |
| `push_front` | `n` раз: добавить `rnd()` в начало | все (для `array` это вставка в позицию 0) |
| `queue` | `n` раз: добавить `rnd()` в конец; затем если `next() mod 3 == 0`, удалить элемент из начала | все (для `array` — удаление элемента 0) |
| `sorted_insert` | `n` раз: `x = rnd()`, **линейным проходом с начала** найти первый элемент строго больше `x` и вставить `x` перед ним (или в конец). Затем `n / 2` раз (целочисленное деление): `p = next() mod len`, линейным проходом дойти до позиции `p` и удалить её | `array`, `linked` |

В `sorted_insert` для массива тоже нужен **линейный** поиск, а не бинарный:
иначе структуры сравниваются в неравных условиях. Порядок вызовов генератора
важен: он в точности такой, как в таблице.

### Формат

**Вход** — одна JSON-строка в stdin:

```json
{"container": "linked", "workload": "sorted_insert", "n": 1000, "seed": 7}
```

**Выход** — одна JSON-строка: длина итоговой последовательности и
контрольная сумма, которая проверяет и содержимое, и порядок элементов:

```
checksum = Σ (i + 1) · aᵢ  mod 1 000 000 007,   i = 0 … len − 1 (с начала)
```

```json
{"len": 500, "checksum": 644103494}
```

Никакого времени и отладочного вывода в stdout: он сравнивается как JSON.

### Примеры

| Вход (`container` любой допустимый) | Выход |
|---|---|
| `{"workload": "push_back", "n": 10, "seed": 42}` | `{"len": 10, "checksum": 37734771}` |
| `{"workload": "push_front", "n": 10, "seed": 42}` | `{"len": 10, "checksum": 35871179}` |
| `{"workload": "queue", "n": 10, "seed": 42}` | `{"len": 6, "checksum": 10306664}` |
| `{"workload": "sorted_insert", "n": 10, "seed": 42}` | `{"len": 5, "checksum": 10682107}` |
| `{"workload": "sorted_insert", "n": 1000, "seed": 7}` | `{"len": 500, "checksum": 644103494}` |

Результат не зависит от структуры: все три обязаны давать одинаковый ответ.
Закрытые тесты — `n ≤ 2000`, все допустимые пары «структура × сценарий».

## Часть 2. Отчёт `REPORT.md`

Замеры делаются локально, отдельной программой или режимом запуска на ваш
выбор (не через точку входа, которую проверяет платформа).

1. **Прогноз до замеров.** Таблица «структура × сценарий» с ожидаемой Big O
   всего сценария. Её нужно закоммитить **раньше** замеров: это видно по
   истории git.
2. **Замеры.** Для каждой пары — не меньше 4 значений `n`, покрывающих не
   меньше двух порядков (например, 10³…10⁵). В каждой точке не меньше 5
   прогонов на разных `seed`, в таблицу идёт **медиана** (метод Монте-Карло
   из лекции). Самый долгий прогон — не больше ~10 с, подберите сетку под
   свой язык.
3. **Сборка с оптимизациями**, иначе замеры бессмысленны: C++ — `-O2`, Rust —
   `--release`, Zig — `-Doptimize=ReleaseFast`. Укажите в отчёте, как
   собирали, и характеристики машины.
4. **Графики** время(n) в логарифмическом масштабе по обеим осям: картинка в
   репозитории или `xychart` в Mermaid.
5. **Выводы.** Где замер совпал с прогнозом, а где нет, и почему. Как минимум
   ответьте: у `sorted_insert` вставка в список — O(1), почему же список
   проигрывает массиву? Удобно считать через доли: сколько времени уходит на
   поиск позиции, а сколько на саму вставку.

### Требование для вашего языка

| Язык | Дополнительно |
|---|---|
| C++ | Добавьте вариант `array` с `reserve(n)` в `push_back` и объясните разницу через амортизированную сложность |
| Rust | Курсоры `LinkedList` нестабильны, поэтому вставка в середину делается через `split_off` + `append`. То же, что для C++, с `Vec::with_capacity(n)`. Плюс: документация `LinkedList` советует почти всегда брать `Vec` или `VecDeque`; подтвердите или опровергните это своими замерами |
| Zig | Узлы списка выделяйте двумя аллокаторами: `std.heap.DebugAllocator` (бывший `GeneralPurposeAllocator`) и `ArenaAllocator`. Сравните время и объясните разницу (задел на лекцию 6) |
| Go | Свой кольцевой буфер для `deque` с ростом ×2. Измерьте число аллокаций (`runtime.ReadMemStats`, поле `Mallocs`) для `linked` и `array` и объясните, как они влияют на GC |
| Python | Свой двусвязный список на классе с `__slots__`. Объясните, почему `list.insert` в середину за O(n) обгоняет ваш список на `sorted_insert`: что на самом деле двигает `list` в памяти |

## Вопросы на защите

1. Какой сценарий сильнее всего расходится с прогнозом Big O и почему?
2. Что такое кэш-локальность и где она видна на ваших графиках?
3. Почему нужна медиана, а не среднее и не один прогон?
4. Если бы в `sorted_insert` у списка была готовая ссылка на позицию вставки,
   кто бы выиграл? Где такое бывает на практике? (Подсказка: LRU.)

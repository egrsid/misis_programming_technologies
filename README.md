# Ownership graph

Вы пишете «движок владения»: интерпретатор маленькой программы, в которой
объекты держат друг друга через **сильные** и **слабые** ссылки, а память
освобождается детерминированно — в момент, когда исчезает последняя сильная
ссылка. Это модель `shared_ptr` / `weak_ptr` из лекции про RAII: нужно
воспроизвести порядок вызова деструкторов, каскадное освобождение полей, утечки
на циклах и то, как слабая ссылка их лечит.

## Модель

- **Объект** создаётся с `f` полями (0 ≤ f ≤ 4). Объекты нумеруются
  `0, 1, 2, …` в порядке создания (`N`). Каждое поле — слот.
- **Слот** (поле объекта или переменная) — одно из трёх: пусто, **сильная**
  ссылка на объект, **слабая** ссылка на объект. Сильная ссылка владеет
  объектом, слабая — нет.
- Объект **жив**, пока на него есть хотя бы одна сильная ссылка. Число сильных
  ссылок — `use_count`. Когда он падает до 0, объект **уничтожается**.
- Слабая ссылка на уничтоженный объект ведёт себя как пустой слот.
- Переменных `V` штук, номера `0..V−1`, сначала все пусты.

**Уничтожение объекта** `o`: сначала в журнал пишется `d<id>`, затем по порядку
полей `0, 1, …, f−1` каждое поле очищается и (если было сильным) освобождается.
Поле `i` освобождается **целиком**, вместе со всеми объектами, которые из-за
этого уничтожатся (в глубину), и только потом идёт поле `i+1`.

**Присваивание в слот**: сначала вычисляется новое значение, оно записывается в
слот, и только потом освобождается старое значение. (Как у `shared_ptr::operator=`:
`a = a` или `a = copy-of-field-of-a` не должны убить объект раньше времени.)

## Операции

Программа — список операций. Все аргументы — целые числа.

| Операция | Действие |
|---|---|
| `N a f` | создать объект с `f` пустыми полями, переменная `a` = сильная ссылка на него |
| `C a b` | `a` = копия слота `b`: сильная остаётся сильной (+1 к счётчику), слабая — слабой, пустая — пустой |
| `M a b` | `a` = слот `b`, `b` становится пустым; при `a == b` ничего не делать |
| `W a b` | `a` = слабая ссылка на объект из `b` (из сильной или слабой); если `b` пуста — пусто |
| `L a b` | `a` = `lock(b)`: если `b` сильная или слабая на живой объект — сильная ссылка на него, иначе пусто |
| `R a` | `a` становится пустой |
| `S v i u` | объект переменной `v` (сильной, либо слабой на живой) получает в поле `i` копию слота `u` (как в `C`) |
| `T v i u` | то же, но в поле `i` кладётся **слабая** ссылка на объект из `u` |
| `F a v i` | `a` = копия поля `i` объекта переменной `v` (как в `C`) |
| `Q v` | в журнал пишется `u<n>`, где `n` — `use_count` объекта из `v` (0, если пусто или объект уничтожен) |

Если объект переменной `v` не существует (пусто или уничтожен) — `S` и `T`
ничего не делают, `F` делает `a` пустой. То же, если `i` ≥ числа полей объекта.

**Завершение.** После последней операции переменные освобождаются в порядке
`V−1, V−2, …, 0` (как локальные в обратном порядке объявления). Затем в журнал
для каждого объекта, который всё ещё жив, **по возрастанию id** пишется
`leak<id>` — такие объекты остались в циклах из сильных ссылок.

## Формат

**Вход** — одна JSON-строка в stdin:

```json
{"vars": 2, "ops": [["N", 0, 1], ["N", 1, 0], ["S", 0, 0, 1], ["Q", 1], ["R", 1], ["Q", 0], ["R", 0]]}
```

Операция — массив: код (строка из одной буквы), затем столько целых, сколько нужно.

**Выход** — одна JSON-строка в stdout: массив строк-событий в порядке их
возникновения (`d…`, `u…`, `leak…`).

```json
["u2", "u1", "d0", "d1"]
```

## Ограничения

| Параметр | Значение |
|---|---|
| Число операций | 0 ≤ n ≤ 3·10⁵ |
| Число переменных `V` | 1 ≤ V ≤ 10⁵ |
| Число полей объекта | 0 ≤ f ≤ 4 |
| Объектов | не больше n |
| Время работы | C++ / Rust — 1 с, Go — 2 с |

Важно: цепочка владения `a → b → c → …` может иметь длину до 10⁵. Деструктор,
который освобождает поля рекурсивно, переполнит стек.

## Примеры

**Пример 1** (из `examples.ndjson`): объект 0 владеет объектом 1.

```json
{"vars": 2, "ops": [["N", 0, 1], ["N", 1, 0], ["S", 0, 0, 1], ["Q", 1], ["R", 1], ["Q", 0], ["R", 0]]}
```
```json
["u2", "u1", "d0", "d1"]
```

- у объекта 1 две сильные ссылки (переменная 1 и поле объекта 0): `u2`;
- после `R 1` объект 1 держит только поле объекта 0; `Q 0` пишет `u1` — это счётчик объекта 0 (его держит переменная 0);
- после `R 0` умирает объект 0 (`d0`), его поле освобождает объект 1 (`d1`).

**Пример 2**: цикл из сильных ссылок.

```json
{"vars": 2, "ops": [["N", 0, 1], ["N", 1, 1], ["S", 0, 0, 1], ["S", 1, 0, 0]]}
```
```json
["leak0", "leak1"]
```

Переменные очищены, но объекты держат друг друга. Если одно из полей заменить
на слабое (`T`), оба объекта умрут.

## Требование для вашего языка

Решение — настоящая реализация владения, а не «таблица ответов»; ограничения
проверяются на ревью.

| Язык | Требование |
|---|---|
| C++ | `std::shared_ptr` / `std::weak_ptr` и деструктор, пишущий в журнал. Следуйте правилу 0: никаких `new`/`delete` и голых указателей-владельцев. Цепочку в 10⁵ звеньев деструктор должен разбирать **без рекурсии** |
| Rust | `Rc` / `Weak` и `impl Drop`, пишущий в журнал. `unsafe` запрещён. Цепочку в 10⁵ звеньев `Drop` должен разбирать **без рекурсии** |
| Go | Деструкторов нет: счётчики ссылок ведутся вручную, освобождение — итеративно. В комментарии объясните, почему `runtime.SetFinalizer` не подходит для этой задачи |

## Вопросы на защите

1. Чем `unique_ptr` отличается от `shared_ptr` по цене и по смыслу владения?
   Где в этой модели «уникальное» владение?
2. Почему цикл из сильных ссылок утекает и как слабая ссылка его чинит?
   Кто в связке «родитель — потомок» должен держать слабую ссылку?
3. Почему рекурсивный деструктор падает на длинной цепочке? Как работает ваш
   итеративный обход и почему он сохраняет порядок `d…`?
4. Что случится в `a = a` или `a = field(a)`, если старое значение освободить
   *до* записи нового?
5. Что в этой задаче соответствует правилу трёх/пяти из лекции?

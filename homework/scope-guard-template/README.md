# Scope guard

Вы пишете «менеджер областей» — интерпретатор программы, где ресурсы
(файлы, блокировки, соединения) открываются внутри вложенных областей, а
ошибки могут случиться где угодно, в том числе **при закрытии**. Нужно, чтобы
каждый открытый ресурс был закрыт ровно один раз и строго в обратном порядке,
что бы ни произошло. Это RAII из лекции: в C++ — деструкторы, в Rust — `Drop`,
в Go — `defer`; и Post-OOP: виды ресурсов описываются интерфейсом / трейтом /
concept'ом, а не иерархией классов.

## Модель

Программа — плоский список операций. Есть неявная **внешняя область**,
закрывающаяся после последней операции.

| Операция | Действие |
|---|---|
| `open kind name` | открыть ресурс `name` вида `kind` (`file`, `lock` или `conn`) в текущей области |
| `work label` | выполнить работу `label` |
| `begin` | открыть вложенную область |
| `try` | открыть вложенную область, **перехватывающую** ошибки |
| `end` | закрыть текущую область (соответствует ближайшему `begin`/`try`) |

Часть операций «ломается» — это задано во входных данных:

- `open` с именем из `fail_open` — ошибка, ресурс **не** открыт;
- `work` с меткой из `fail_work` — ошибка;
- закрытие ресурса с именем из `fail_close` — ошибка закрытия.

### События

В журнал пишутся строки. Сбой помечается `!` в конце первого слова события.

| Что произошло | События |
|---|---|
| `open` успешен | `open <name>` |
| `open` сломан | `open! <name>` |
| `work` успешен / сломан | `work <label>` / `work! <label>` |
| закрытие `file` | `close <name>` |
| закрытие `lock` | `unlock <name>` |
| закрытие `conn` | `flush <name>`, затем `close <name>` |
| ошибка перехвачена | `catch <текст ошибки>` |
| конец программы | `result ok` или `result abort <текст ошибки>` |

Если закрытие сломано, **последнее** событие закрытия получает `!`
(`close! A`, `unlock! L`; у `conn` — `flush C`, затем `close! C`).

**Текст ошибки** — это сломавшееся событие без `!`: `open A`, `work x`,
`close A`, `unlock L`. Для закрытия `conn` это `close C`.

### Правила

1. **Закрытие в обратном порядке.** Область закрывает свои ресурсы в порядке,
   обратном открытию.
2. **Ошибка при выполнении.** Остаток текущей области пропускается (его
   операции не выполняются и ничего не пишут). Каждая область по пути наружу
   закрывает свои ресурсы — внутренняя раньше внешней.
3. **`try` перехватывает.** Область `try` после закрытия своих ресурсов пишет
   `catch <ошибка>`, и выполнение продолжается **после её `end`**. Обычная
   область (`begin`) и внешняя область ошибку пропускают дальше. Внешняя
   область ошибку не перехватывает: после её закрытия — `result abort …`.
4. **Ошибки закрытия при раскрутке подавляются.** Если область закрывается из-за
   уже летящей ошибки, сломанное закрытие только пишет событие с `!`; ошибка не
   меняется. Остальные ресурсы всё равно закрываются.
5. **Ошибка закрытия при нормальном выходе.** Область закрывает **все** свои
   ресурсы; если сломалось несколько, ошибкой становится **первое**
   сломавшееся закрытие (остальные только пишут `!`). Эта ошибка летит наружу
   как обычная — её перехватит собственный `try` этой же области, если он есть.
6. Ошибка внутри пропускаемого остатка не возникает: пропущенное не выполняется.
   `try` внутри пропускаемого остатка ничего не перехватывает.

## Формат

**Вход** — одна JSON-строка в stdin:

```json
{"fail_open": ["D"], "fail_close": [], "fail_work": [],
 "ops": [["open", "file", "A"], ["try"], ["open", "conn", "C"], ["open", "file", "D"], ["end"], ["work", "after"]]}
```

Операция — массив строк. Имена и метки — короткие строки из букв и цифр.

**Выход** — одна JSON-строка в stdout: массив строк-событий.

```json
["open A", "open C", "open! D", "flush C", "close C", "catch open D", "work after", "close A", "result ok"]
```

## Ограничения

| Параметр | Значение |
|---|---|
| Число операций | 0 ≤ n ≤ 2·10⁵ |
| Глубина вложенности областей | ≤ 5000 |
| Ресурсов в одной области | до 10⁵ |
| Скобки `begin` / `try` / `end` | расставлены правильно |
| Время работы | C++ / Rust — 1 с, Go — 2 с |

## Примеры

**Пример 1** — раскрутка: `work boom` падает, закрываются `B`, затем `A`.

```json
{"fail_open": [], "fail_close": [], "fail_work": ["boom"],
 "ops": [["open", "file", "A"], ["begin"], ["open", "lock", "B"], ["work", "boom"], ["open", "file", "never"], ["end"], ["work", "never2"]]}
```
```json
["open A", "open B", "work! boom", "unlock B", "close A", "result abort work boom"]
```

**Пример 2** — подавленные ошибки закрытия: `work boom` ломается, `B` и `A`
закрываются со сбоем, но ошибкой остаётся `boom`.

```json
{"fail_open": [], "fail_close": ["A", "B"], "fail_work": ["boom"],
 "ops": [["try"], ["open", "file", "A"], ["open", "file", "B"], ["work", "boom"], ["end"], ["work", "after"]]}
```
```json
["open A", "open B", "work! boom", "close B!", "close A!", "catch work boom", "work after", "result ok"]
```

## Требование для вашего языка

Закрытие должно быть **автоматическим** (механизм языка), а не вручную в каждой
ветке; вид ресурса задаётся интерфейсом, а не иерархией. Проверяется на ревью.

| Язык | Требование |
|---|---|
| C++ | Область — RAII-класс; деструктор закрывает ресурсы и **не бросает** (`noexcept`). Ошибки — исключения. Виды ресурсов — `concept` + `std::variant`: никакого наследования и `virtual`. Копирование области запрещено (`= delete`) |
| Rust | Область — структура с `impl Drop`; ошибки — `Result` и `?`. Виды ресурсов — трейт (`dyn` или enum — на ваш выбор). `unsafe` запрещён, `panic!` для ошибок программы нельзя |
| Go | Закрытие через `defer`; виды ресурсов — интерфейс с методом `Close`; ошибки — `error`, не `panic`/`recover`. В комментарии объясните, чем `defer` в цикле хуже `defer` в отдельной функции |

## Вопросы на защите

1. Почему деструктор (`~T`, `Drop`) не должен падать? Что делает язык, если он
   всё же бросает во время раскрутки? Как вы обошли это в вашем решении?
2. Почему закрытие при раскрутке обязано подавлять ошибки, а при нормальном
   выходе — нет? Что здесь соответствует `suppressed` исключениям Java?
3. Чем интерфейс / трейт / concept лучше базового класса `Resource` с
   виртуальным `close()`? Что вы теряете (стоимость вызова, открытость набора видов)?
4. Что будет, если область скопировать? Почему копирование запрещено, а
   перемещение допустимо?
5. Вложенность 5000: что происходит со стеком вызовов и чем итеративный
   интерпретатор отличается от рекурсивного?
